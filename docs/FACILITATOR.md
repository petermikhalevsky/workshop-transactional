# Facilitator guide — Transactional War Room (90 минут)

## До занятия

```bash
docker compose down -v
docker compose up -d --build
./scripts/health-check.sh          # exit 0
./scripts/start-load.sh 60 20      # проверить, что инцидент воспроизводится
sleep 35
./scripts/health-check.sh          # exit 2
docker compose --profile load stop load-generator
./scripts/reset-workshop.sh
```

Проверьте, что Grafana открывается без логина и дашборд наполняется. Стенд должен
воспроизводить инцидент за 30–60 секунд, иначе занятие развалится по таймингу.

## Роли в группе

| Роль | Задача |
|---|---|
| driver | выполняет команды, не импровизирует |
| metrics | читает Grafana, называет числа |
| evidence | собирает дампы и логи, следит, чтобы ничего не рестартнули |
| skeptic | проверяет гипотезы: «а чем это доказано?» |

Ведущий не показывает код, пока группа не сформулирует гипотезу и не подкрепит её
метриками.

## Тайминг

### 0–5 мин. Установка

Стенд уже поднят. Показать Grafana и объяснить, что management-порт 8081 — это
отдельная дверь для диагностики.

### 5–15 мин. Симптом

```bash
./scripts/start-load.sh 600 20
```

Дать 30–60 секунд. Попросить группу назвать симптом **числами**: p95, долю
таймаутов/no-response, `pending`, `active`. Зафиксировать время начала.

Ожидаемая картина через минуту:

| Показатель | Значение |
|---|---|
| p95 HTTP (завершённые заказы) | ≈ 0,9 с |
| max latency у клиента | упирается в клиентский таймаут (15 с) |
| no-response / таймауты | растут после ~30 с |
| `hikaricp_connections_active` | 10 |
| `hikaricp_connections_idle` | 0 |
| `hikaricp_connections_pending` | > 0 |
| `workshop_transactions_active` | 10 |
| CPU | низкий |

`503 DB_POOL_TIMEOUT` — не обязательный симптом: он появляется, только если запрос
дождался Hikari и провисел там все 10 секунд. При плавной нагрузке очередь
рассасывается быстрее, и клиент видит таймаут, а не 503.

### 15–30 мин. Гипотезы

Вопросы, которые нужно задать:

1. Сервис жив? (`/api/health`, liveness)
2. Это CPU, память, GC или сеть?
3. Это база? Проверить `db-sessions.sh`.
4. Это дедлок? Сравнить `BLOCKED` и `WAITING`.
5. Если все соединения заняты, то **чем**?

Гипотеза принимается только с метрикой. «Кажется, пул» — не гипотеза.
«`active=10`, `idle=0`, `pending` растёт» — гипотеза.

### 30–45 мин. Улики

```bash
./scripts/thread-dump.sh
./scripts/diagnose-thread-dump.sh artifacts/thread-dump-*.txt
./scripts/db-sessions.sh
```

Ожидаемые факты:

- 10 потоков в `PaymentGateway.authorize`, внутри — `socketRead0`;
- 20–30 потоков в `HikariPool.getConnection`;
- `BLOCKED` около нуля: это очередь, а не дедлок;
- в PostgreSQL 10 сессий `idle in transaction`, `pg_blocking_pids` пуст;
- в логах `=== CONNECTION POOL EXHAUSTED ===`.

Ключевой вывод: **соединения удерживаются внешним вызовом, а не работой с БД.**

### 45–55 мин. Причина

Показать код `OrderService`:

```java
@Transactional
public OrderResult placeOrder(...) {
    orders.save(...);                 // соединение занято
    paymentGateway.authorize(...);    // 800 мс внешнего вызова
    paymentAttempts.save(...);        // всё ещё та же транзакция
}
```

Посчитать: 10 соединений / 0,8 с = 12,5 заказов в секунду максимум. Нагрузка 20/с.
Очередь растёт; часть запросов висит до клиентского таймаута, а те, что дождались
Hikari и провисели `connection-timeout=10000`, получают 503 `DB_POOL_TIMEOUT`.

Разобрать альтернативы и их цену:

| Вариант | Что даёт | Цена |
|---|---|---|
| увеличить пул | отсрочка | больше соединений, очередь вернётся |
| увеличить timeout | ошибки позже | latency ещё хуже |
| @Async / очередь | сложнее | нужна идемпотентность и retry |
| разнести транзакции | лечит причину | нужна аккуратность с partial failure |

### 55–70 мин. Фикс

Ветка `solution`:

```bash
git checkout solution
docker compose up -d --build order-service
./scripts/start-load.sh 300 20
```

Суть фикса: `OrderService` перестаёт быть `@Transactional` и становится
оркестратором; `OrderPersistenceService` открывает короткие транзакции только
вокруг операций с БД; вызов шлюза выполняется между ними.

Важно проговорить: после `createPending` заказ уже в БД. Если шлюз упал, заказ
помечается `FAILED` отдельной транзакцией. Это осознанный компромисс: лучше
видимый `FAILED`, чем откат всего и потерянный платёж.

### 70–80 мин. Приёмка

```bash
./scripts/verify-fix.sh
```

Критерии: exit 0,
`workshop_payment_call_seconds_count{scope="inside_transaction"} = 0`,
`workshop_pool_saturated = 0`, клиентских таймаутов и 5xx нет, p95 < 1,5 с.

### 80–90 мин. Постмортем

Заполнить `POSTMORTEM_TEMPLATE.md`. Обязательно ответить: какая метрика поймала бы
проблему раньше и какой алерт нужно добавить.

## Подсказки по возрастанию

1. «Посмотрите на management-порт, а не только на 8080».
2. «Сравните active, idle и pending».
3. «Кто держит соединение? Посмотрите `workshop_transactions_active`».
4. «Снимите дамп и найдите, что делают потоки с соединением».
5. «Проверьте в PostgreSQL, есть ли блокировки».
6. «Сколько времени занимает внешний вызов и сколько — транзакция?»
7. «Откройте `OrderService` и посмотрите границы `@Transactional`».

## Частые неверные гипотезы

| Гипотеза | Чем опровергается |
|---|---|
| «Мало соединений в пуле» | 10 соединений заняты непрерывно, хотя каждый заказ длится ~0,9 с — вопрос в удержании, а не в количестве |
| «PostgreSQL тормозит» | `db-sessions.sh`: блокировок нет, запросы быстрые, сессии idle in transaction |
| «Дедлок» | `BLOCKED ≈ 0`, цикла в дампе нет, потоки в `WAITING` |
| «Утечка памяти / GC» | heap ровный, CPU низкий |
| «Медленный платёжный шлюз» | p95 вызова 0,8 с — норма; проблема в том, что вызов держит соединение |
| «Надо просто перезапустить» | рестарт убирает симптом, причина остаётся |


сломанную версию.
